# Premier démarrage et décideurs

## Parcours

L’assistant apparaît depuis un catalogue vide ; une configuration existante garde son écran habituel. Il reste accessible depuis État. Ses étapes sont modèles répondants, décideur facultatif, règles, test explicite. Le WebView conserve uniquement un marqueur `{open, step}` dans `omr:onboarding:v1` : un premier parcours interrompu reprend automatiquement, tandis qu’une configuration valide préexistante sans marqueur n’est pas forcée. Quitter l’assistant ferme ce marqueur ; aucun secret ni brouillon n’y est enregistré. Chaque enregistrement reprend le CAS existant. Les secrets passent par le coffre OS, jamais par un brouillon persistant. Une interruption ne déclenche ni génération, ni téléchargement, ni démarrage au prochain lancement. Les routes directes restent utilisables sans décideur.

Les répondants utilisent Responses dans le parcours guidé. Les configurations avancées Chat Completions et Messages existantes restent accessibles. Découvrir un catalogue n’établit ni les capacités ni la génération. Un test de génération ou de décision exige son propre clic indiquant son coût possible ; ni l’enregistrement ni la navigation ne lance d’inférence.

## Trois modes

- **Clé API (BYOK)** : destination HTTPS, modèle exact, clé dans le coffre. Le décideur JSON Chat Completions utilise pi-ai, sans `response_format` non pris en charge, puis valide strictement le JSON. Pas de retry ni de repli. Le protocole Jev/SystemOne utilise `jev_decider.decide`, `/systemone` et son véritable décodeur `answers.route` ; jamais un modèle chat de remplacement. La politique Jev mappe direct à qualité 1, reasoning à 3.
- **Serveur existant** : URL `/v1` (Ollama : `http://127.0.0.1:11434/v1`), modèle déjà installé. OMR ne démarre ni n’arrête ce serveur. Même contrat JSON pour un modèle chat ; la connexion keyless reste possible. Les modèles arbitraires et les installations Ollama ne sont pas qualifiés par un simple catalogue accessible.
- **Modèle géré** : `scombat/s1d1-router-6src-tiny-onnx-int8`, révision `dac13b5c0356864ea4501fa151d74dcd8b3ea22a`. Téléchargement public explicite des six fichiers SHA-256 épinglés dans `omr.S1D1_FILES`, sans secret ni contexte envoyé. Poids hors Git, dans le dossier privé de l’application. Un ensemble complet est vérifié avant publication atomique ; reprise = nouvelle tentative explicite, sans réutiliser de téléchargement partiel. États : absent, téléchargement, installé, démarrage, prêt, arrêté, annulé, erreur. Annuler interrompt le travail possédé et nettoie ses fichiers temporaires ; les poids validés restent installés. Démarrer/arrêter sont explicites et ne modifient pas les serveurs externes.

## Contrat local s1d1

Le worker isolé charge ONNX CPU, tokenizers et numpy depuis le moteur gelé (pas le Python utilisateur). Il vérifie les empreintes avant et après chargement, désactive la troncature du tokenizer et refuse plus de 1024 tokens. L’entrée est le dernier message utilisateur textuel complet du contexte borné ; les pièces multimodales sont refusées. Ce classifieur de prompt n’interprète pas l’historique comme un modèle conversationnel. Les poids fournissent 21 sorties hétérogènes : la complexité est `clip(0.5 + 0.25 * sortie[0], 0.01, 1)` ; pas de softmax global. Seuils produit expérimentaux : `<0.375 → 1`, `<0.625 → 2`, sinon `3`. Ils ne prouvent ni une qualité minimale calibrée ni une économie. Motif enregistré : `task_requirement`. Aucun prompt ni sortie libre du modèle n’est conservé.

Le chargement et le téléchargement utilisent chacun un processus possédé, un HOME/cwd temporaire, un environnement fermé et des canaux privés. Le téléchargement est borné à 300 secondes, y compris un résolveur DNS bloqué : annulation et arrêt tuent le groupe entier (bootloader gelé compris). Une demande d’annulation reste active jusqu’au nettoyage du staging ; l’arrêt du moteur n’est acquitté qu’après la fin du worker et ce nettoyage. Le mode géré utilise les groupes de processus POSIX sous Linux et macOS ; le candidat ARM macOS a sa qualification native distincte. Windows reste explicitement indisponible sur cette branche tant que son runtime et son nettoyage ne sont pas qualifiés. Une décision est bornée par le deadline du gateway et annulable dès le premier octet écrit sur le canal privé, écriture complète et lecture comprises, même si le worker ne consomme plus stdin. Expiration et annulation tuent puis réapent le groupe possédé. Une décision encore en cours lors d’un arrêt/redémarrage reste liée à son ancien processus : sa fin ou son erreur ne peut ni arrêter le nouveau worker ni modifier son état. Aucun chargement ou démarrage automatique après relance. Une destination de consentement comprend le mode et le protocole lorsqu’ils sont explicites ; changer URL, connexion, modèle, mode ou protocole révoque l’accord. L’historique ne peut pas le réactiver.

## Ollama SystemOne

Pour un modèle natif tel que `d3:4b`, sélectionner explicitement **Ollama · SystemOne** et une connexion Ollama `/v1`. OMR utilise `/systemone`, jamais Chat Completions. Le choix, ses probabilités normalisées et la confiance doivent être valides ; la confiance ne doit pas nécessairement égaler la probabilité maximale. Les champs d’abstention et d’inconnu absents ne sont pas inventés ; s’ils sont présents, une abstention ou une probabilité d’inconnu supérieure à 0,25 entraîne un refus. L’usage absent reste inconnu. Le délai propre à cet appel est de 60 secondes au maximum, toujours borné par l’échéance globale et l’annulation ; aucun préchauffage ni repli n’est implicite. Les captures D3 documentent un démarrage à froid de 30,743 secondes, sans garantir une durée future. Le test de génération de l’interface impose sa propre limite globale de 20 secondes : il peut donc expirer avant un chargement à froid même si le gateway laisse plus de temps.

## Imajev : serveur spécialisé, pas un substitut chat

Le premier appel peut inclure le chargement à froid du modèle : OMR laisse au maximum 30 secondes à cet appel SystemOne, sans dépasser l’échéance globale ni ignorer l’annulation. Une abstention ou une probabilité d’inconnu supérieure à 0,25 reste une décision refusée ; aucun modèle de remplacement n’est choisi automatiquement. Le succès des conversations multi-tours et des outils dépend des décisions réelles du modèle et doit être qualifié séparément.

L’option Imajev ne charge pas son adaptateur dans Ollama ni dans un générateur GGUF. Elle vise un serveur Imajev déjà lancé avec son vrai décodeur de readout (LoRA + codes d’options + unknown), exposant `/v1/systemone`. Contrat inspecté : `src/vision_decision/jev_api.py` à la révision amont `318e8dad55c12a1c6faddbec5f30489d2ee529ff` de [mohit67890/imajev](https://github.com/mohit67890/imajev). OMR envoie une question `choice` sur les qualités 1/2/3 et décode `answers.quality` : probabilités connues renormalisées, choix maximal, confiance finie, `abstained=false`, `unknown_probability ≤ 0.25`. Ce dernier seuil est une politique produit prudente, non calibrée. Une abstention, une masse inconnue trop forte ou une réponse malformée est un refus de routage, jamais un repli chat. Le modèle retourné doit correspondre exactement au modèle déclaré ; l’usage absent reste inconnu. Les identifiants contenant `imajev` sont refusés sur l’adaptateur chat. Le serveur et les poids Imajev ne sont pas qualifiés par les fixtures de protocole ; le checkpoint local réellement qualifié ici reste s1d1.

## Qualification

Les tests offline distinguent fixtures de transport et inférence locale réelle. La remise indique exactement le checkpoint, les dépendances, l’hôte, le binaire et les parcours exercés. Les clés API payantes, sessions d’abonnement, macOS et Windows ne sont pas qualifiés par le parcours Linux. Les scripts packaging/runtime et leurs licences appartiennent au chantier de distribution séparé ; aucune publication n’est autorisée ici.
