# Contrat OMR Desktop v1

## Frontières

Tauri v2 possède un seul moteur Python gelé par PyInstaller, piloté par JSON Lines sur stdin/stdout privés. Il ne dépend pas du Python de l'utilisateur. Les commandes natives sont `snapshot`, `save_config`, `discover`, `test_generation`, `credentials`, `export_receipts` et `set_secret`. Aucun shell ni fichier arbitraire n'est accessible au WebView. Le gateway existant reste responsable des formats Chat Completions, Responses et Messages. Le transport HTTP direct conserve les octets ; le transport `pi-ai` sélectionnable réutilise les parseurs/encodeurs et adaptateurs du paquet épinglé, via un exécutable Bun embarqué dans le sidecar. Voir [PI-AI.md](PI-AI.md) pour le périmètre qualifié et les options refusées. Son extension desktop est optionnelle, sans changement du contrat CLI historique.

Le gateway desktop écoute exclusivement 127.0.0.1 sur un port attribué par l'OS ; chaque requête, catalogue compris, exige un bearer aléatoire propre au lancement. Origin et Host étrangers sont refusés. Les clés fournisseurs transitent uniquement par IPC privé puis restent en mémoire du moteur et, pour pi-ai, de son processus dédié ; Tauri les lit/écrit dans le coffre OS. Aucun stockage localStorage, export de clés ou import de sessions natives. Le coffre indisponible est une erreur, jamais un repli JSON.

## Configuration et catalogue

Le fichier `providers.json` est synchronisé dans les deux sens avec l’UI ; `config.json` conserve la dernière configuration valide. Voir [format, chargement et concurrence](PROVIDERS-FILE.md). Le rechargement passe par `save_config` avec `source: "file"` et la révision attendue, sans chemin fourni par le WebView.

La réponse HTTP peut arriver avant la finalisation du reçu : le gateway l'enregistre dans son `finally`, puis décrémente `active`. Un `snapshot` est pris sous verrou ; après une requête isolée, attendre `active == 0` et un nouveau reçu avant de vérifier ses champs. Un client ne doit pas supposer que la fin de lecture HTTP rend le reçu immédiatement visible.

Configuration versionnée par révision, remplacement compare-and-swap et historique local des métadonnées (sans clés). Les requêtes en cours gardent leur snapshot ; les suivantes utilisent les nouveaux réglages. Restaurer passe par le même CAS. Connexions identifiées par UUID ; modèles identifiés par UUID stables, amont conservé exactement. IDs publics : `omr/economy`, `omr/balanced`, `omr/quality`, `direct/<connexion UUID>/<modèle UUID>`. Le direct ignore le décideur, ne change ni modèle ni effort demandé ; un effort imposé contradictoire est refusé. Pas de repli automatique.

Les états annoncé, configuré, découvert et génération vérifiée sont distincts. La découverte explicite effectue seulement GET /v1/models. Les modèles sont déclarables manuellement. Une génération de vérification exige un clic portant son coût possible ; aucun test payant automatique. Une souscription native n'est pas un accès API portable : seuls les endpoints API compatibles et sans authentification locale sont pris en charge ici.

## Décision

Le décideur est interchangeable via l’interface `classify(context, candidates, stopped, deadline)`. Les trois modes et leur cycle de vie suivent [ONBOARDING.md](ONBOARDING.md) : BYOK, serveur existant par URL et s1d1 ONNX téléchargé/géré explicitement. Le protocole chat JSON utilise pi-ai pour les nouvelles connexions ; Jev utilise son protocole SystemOne et son décodeur réel. Toute transmission de contexte exige un consentement pour la destination exacte. Le booléen de configuration ne vaut pas nouvel accord : `save_config` accepte `consent_for: {connection, url, model}` seulement à la suite d’un clic explicite pour cette destination exacte. Sans ce nouvel accord, il conserve un consentement uniquement si la destination déjà consentie reste inchangée ; changer connexion, URL ou modèle le révoque. L’accord actif est persisté séparément avec son identité exacte ; le démarrage refuse un booléen sans cette liaison ou une destination différente. L’historique de restauration contient toujours `consent=false` et ne peut réactiver un accord. L’interface invalide aussi le brouillon et son accord en attente dès que cette identité change. Sans décideur, les profils sont visibles mais refusent explicitement de router ; les routes directes restent utilisables. Aucun classifieur constant n'est livré.

Le décideur renvoie une exigence de qualité déclarée 1/2/3 et un motif dans une énumération bornée, jamais du texte libre enregistré. Les niveaux qualité des modèles sont des préférences déclarées par l'utilisateur, pas des benchmarks. Les profils appliquent un plancher de qualité puis classent selon tarifs déclarés et qualité ; les inconnues restent inconnues. Coût attendu : tokens de contexte estimés + sortie attendue configurée. Changer exige un bénéfice estimé supérieur au coût de retransmission et à la marge configurée ; cache inconnu non déduit. Une montée de qualité justifiée peut changer même si plus chère. Réévaluation par défaut à chaque nouveau tour utilisateur ; les cycles outils restent attachés. Désactivation fige la route par session et profil. Un profil différent ou un direct n'hérite pas d'une affinité contradictoire. Sessions bornées, non persistées. L’affinité épingle connexion, URL, modèle amont, protocole et effort effectif exacts, pas seulement l’UUID du modèle. Une continuation exige encore la capacité outils même si le client ne répète pas `tools`. Le tour logique courant remonte au dernier message utilisateur sans résultat d’outil : un préremplissage assistant après un appel/résultat ne termine pas le cycle ; un nouveau message utilisateur sans résultat d’outil permet la réévaluation, même si l’historique contient des outils. Une continuation outils ou une session sans réévaluation refuse `continuity_route_unavailable` si sa route est révoquée, modifiée ou incompatible ; elle ne reclassifie jamais silencieusement. Un nouveau tour avec réévaluation peut choisir une autre route autorisée.

Le budget du décideur est borné par octets UTF-8 (estimation conservatrice 1 octet/token, pas tokenizer exact). Défauts provisoires explicites : extrait 4096 tokens estimés, enveloppe totale 8192, maximum 12 messages ; mesurés par tests synthétiques, pas optimisés par benchmark. Les groupes d'outils ne sont pas coupés : au besoin seul le dernier tour utilisateur complet est transmis ; s'il dépasse le budget, refus sans synthèse ni escalade payante. Le modèle répondant reçoit l'intégralité du payload original.

## Observabilité et cycle de vie

Les reçus gardent seulement identités locales, modèle demandé/confirmé, effort, candidats, profil/version, motif enum, estimations, durée, erreurs enum et usage numérique observé. Ni prompt, ni résultat, ni erreur fournisseur brute. L'identité amont est confirmée seulement si elle correspond exactement au modèle demandé. Entrée/sortie/cache/raisonnement restent séparés ; cache et raisonnement sont des sous-catégories, pas ajoutés au total. Surcoût du décideur séparé, échecs connus inclus. Comparaison à référence versionnée : repricing à volume identique, pas facture ni tokens économisés. Sans tarifs ou usage complets, non mesuré. Historique admissible : 30 jours de choix directs, fréquence par modèle ; aucun défaut inventé en l'absence d'historique.

Fermer minimise la fenêtre sous Linux pour rester accessible sans tray ; ailleurs, masque uniquement si un tray a été créé. Quitter exige une action explicite et refuse tant que des requêtes sont en cours (sauf arrêt forcé explicitement confirmé). Chaque ouverture, fermeture, annulation (bouton, Échap ou croix) et tentative d’arrêt consomme/réinitialise l’accord d’interruption ; une nouvelle tentative exige un nouveau clic. Pas de redémarrage après configuration. Menu macOS et fenêtre Windows/Linux ; autostart configurable via plugin natif. Compaction/délégation HTTP : non disponibles ; les commandes de session native isolée sont décrites ci-dessous. Liens de conversations : non disponibles sans intégration vérifiée.

## Sessions de stratégies natives

Le contrôle privé `native` et les disponibilités suivent [NATIVE-STRATEGIES.md](NATIVE-STRATEGIES.md). Il crée uniquement une session Codex isolée sur l'hôte qualifié ; aucune reprise de session utilisateur, aucun transfert de souscription vers le gateway API, aucune activation automatique. Les travaux natifs comptent dans le refus de quitter sans interruption. Les reçus natifs contiennent des snapshots numériques séparés des totaux API et des coûts auxiliaires inconnus, jamais le contexte ou le résultat.

## Playground Chat

La section Chat utilise réellement Vercel AI SDK `useChat` avec un transport IPC natif (`chat_start`, `chat_poll`, `chat_cancel`). Les modèles activés sont groupés par fournisseur ; un décideur consenti rend aussi accessibles les trois profils OMR. Les conversations texte restent en mémoire et chaque session épingle sa route directe ou son profil, ainsi que sa révision de configuration. Le moteur existant choisit le modèle concret des profils parmi les candidats compatibles avec le protocole affiché, sans conversion. L’identité confirmée vient du reçu exact du tour. Arrêt et fermeture du Chat annulent jusqu’au socket amont ; ni retry, ni fallback, ni serveur Node, ni assouplissement CSP/CORS. Voir [le contrat et les vérifications Chat](CHAT.md) pour les limites et preuves source.

## Vérification et packaging

Tailwind lit exclusivement `src/` et `index.html`, indépendamment de Git et des fichiers de build voisins. `npm run test:build` compare deux builds isolés avec et sans sources étrangères : les octets JS/CSS doivent être identiques. Cela vérifie le périmètre des entrées frontend, pas la reproductibilité binaire des paquets natifs.

`python3 -B -m unittest test_desktop -v`, suites historiques CI, `npm ci`, `npm ci --prefix provider-runtime`, `npm run check --prefix provider-runtime`, `npm run build --prefix provider-runtime`, `npm test`, `npm run check`, `npm run format:check`, `npm run build`, `cargo test --locked`, `cargo clippy --locked -- -D warnings`, `cargo fmt --check`, puis `npm run native:build` dans `desktop/`. `scripts/build_sidecar.py` produit le binaire pour le triple hôte ; aucune compilation croisée n'est une validation native. Aucun workflow de publication ajouté. Les hôtes non exercés sont signalés dans la remise release.

La régression HTTP `python3 -B -m unittest test_desktop_packaged -v` utilise par défaut le sidecar source. `OMR_TEST_ENGINE=/chemin/absolu/omr-engine` exécute le même parcours sur le binaire extrait de chaque paquet, avec `PATH=/nonexistent` : préremplissage ordinaire, continuité outils avec préremplissage sans nouvel appel décideur, révocation refusée sans transmission et nouveau tour utilisateur réévaluable. État et API de test sont isolés et synthétiques.
