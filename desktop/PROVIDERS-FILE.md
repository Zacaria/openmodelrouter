# Fournisseurs : fichier éditable et sélecteurs

## Fichier et rechargement

`providers.json` est dans le dossier de données de l’application, à côté de `config.json`. L’interface affiche son **chemin absolu réel** ; ne pas supposer un chemin macOS depuis Linux. `config.json` reste l’état interne de dernière configuration valide, révision, historique et consentement. Ne pas l’éditer pour configurer les fournisseurs.

Le fichier public contient directement l’objet `Config` décrit dans `src/types.ts` : `connections`, `reevaluate`, `context_tokens`, `total_tokens`, `max_messages`, `expected_output`, `switch_margin`, `baseline`, `decider`. C’est le même format que le brouillon UI, pas une exportation à réimporter ailleurs. Le moteur le crée au premier lancement depuis la dernière configuration valide. Un enregistrement UI écrit ce fichier lisible (JSON UTF-8 indenté), puis conserve l’état interne. Aucun champ clé API, token ou session n’est accepté. Les clés restent au coffre OS, indexées par UUID de connexion. L’état interne conserve durablement la liaison de chaque UUID accepté à son URL exacte, y compris les UUID supprimés, indépendamment du chargement des clés et des dix révisions d’historique. Une autre URL exige une nouvelle connexion avec un nouvel UUID et l’enregistrement explicite de sa clé ; retirer une clé ou une connexion, resynchroniser le coffre ou redémarrer ne libère pas son UUID. Ce contrôle s’applique aux sauvegardes UI comme au fichier, avant toute utilisation de credentials. Le fichier ne peut pas non plus changer le transport d’une connexion présente ; l’UI peut changer HTTP/pi-ai à URL inchangée.

Une connexion restaurée depuis le fichier qui n’était pas présente au lancement ne récupère pas automatiquement une ancienne clé du coffre : la réenregistrer explicitement dans OMR ou redémarrer pour recharger les clés natives. L’interface ne transforme pas sa présence dans le fichier en preuve d’authentification.

Les connexions gardent `id` (UUID stable), `name`, `url`, `transport` (`pi-ai` ou `http`) et `models`. Chaque modèle garde `id` (UUID), `upstream` exact, `protocols`, `enabled`, `tools`, `quality` (préférence 1–3), `input_price`, `output_price`, `effort`. Les prix inconnus et l’effort non imposé valent `null`. Les capacités sont déclarées, pas déduites d’un nom. La découverte seule ne configure aucun modèle. Un modèle ajouté (manuellement ou coché dans le catalogue) est activé, sans déclaration de compatibilité outils ni vérification de génération.

1. Modifier les réglages dans OMR : ils sont enregistrés automatiquement après 350 ms sans édition. L’état visible distingue attente, écriture, succès et refus ; aucun bouton « Appliquer ».
2. Modifier `providers.json` avec un éditeur et enregistrer.
3. Cliquer **Charger le fichier**. L’opération refuse les brouillons UI non enregistrés : corriger le refus ou les abandonner explicitement avant le chargement.
4. Une configuration valide devient effective aux prochaines requêtes. Les requêtes déjà parties gardent leur snapshot. Au démarrage, les changements valides sont aussi chargés ; un fichier invalide conserve la dernière configuration valide et affiche son refus.

### Sauvegarde automatique et catalogue

Une seule écriture est en vol. Les éditions en attente sont coalescées, et un résultat ancien ne remplace jamais une édition plus récente. La révision CAS avance uniquement après succès ; un refus conserve le brouillon et la dernière configuration valide, arrête les reprises automatiques jusqu’à une nouvelle édition ou une relance explicite. Abandonner attend la fin de l’écriture en vol avant de reprendre le dernier état accepté. Pendant cet abandon ou le chargement du fichier, les contrôles de configuration sont temporairement indisponibles jusqu’à la fin du rechargement ; une indication visible explique cette attente. Les actions clé, découverte et test vident d’abord la file ; un échec annule l’action avec un message visible, au lieu de désactiver silencieusement son bouton. La saisie d’une clé et sa confirmation restent explicites et passent seulement par le coffre OS. Les éditions ultérieures pendant une action restent en attente de sauvegarde.

Le catalogue découvert est un sélecteur compact défilant : recherche insensible à la casse sur l’identifiant exact, cases à cocher, compteurs sélectionnés/total et résultats visibles. OpenRouter est regroupé par le préfixe avant `/` ; les autres connexions restent sous leur nom de fournisseur. **Tout sélectionner** ajoute les résultats affichés et **Effacer** retire uniquement les résultats affichés, sans perdre les choix masqués ni modifier les modèles manuels hors catalogue. La portée et le nombre des résultats sont visibles. Cocher ajoute immédiatement le modèle aux réglages ; décocher le retire. Les réglages existants des modèles conservés ne sont pas réinitialisés. Un identifiant manuel vide reste dans le brouillon refusé tant qu’il n’est pas corrigé. Le bouton de génération s’appelle **Tester** ; le dialogue conserve le prompt, la destination et l’avertissement de coût avant confirmation. Les codes de diagnostic transmis par la lane moteur (contrat `desktop/GENERATION-TEST.md` du candidat `693c5141413da65c324014ce684d803f2614f420`, à composer après sa revue) reçoivent des messages dédiés. L’UI relit le snapshot après un refus, conserve l’état d’échec dans le résumé replié et montre le diagnostic sûr une fois déplié, sans afficher de texte amont arbitraire. Ces messages n’établissent aucune cause pour un essai fournisseur historique.

Le rechargement externe ne peut jamais accorder un consentement au décideur : son booléen est remis à `false`. Reconfirmer sa destination dans l’interface. Les sauvegardes normales préservent l’accord uniquement pour la destination exacte inchangée. Un échec de validation ou une modification concurrente ne remplace ni le fichier édité ni la dernière configuration valide. La comparaison porte sur les octets du fichier (SHA-256), en plus de la révision UI, immédiatement avant remplacement atomique. C’est une détection optimiste : aucun verrou ne peut empêcher un éditeur externe ignorant les verrous d’écrire après cette vérification. Si l’écriture interne échoue après l’écriture publique, le moteur conserve son ancien état et refuse les sauvegardes jusqu’au chargement explicite ; le prochain démarrage reprend le fichier valide.

IPC existant, sans nouvelle allowlist Rust : `save_config` accepte soit `{config, revision, consent_for?}`, soit `{source: "file", revision}`. Le second ne reçoit pas de chemin arbitraire. Les snapshots incluent `config_file: {path, status}` (`synced`, `changed`, `invalid`, `unavailable`).

Les limites de métadonnées sont explicites : 32 connexions, 4 096 modèles déclarés au total, fichier de 4 Mio et réponse de découverte de 16 Mio. Elles bornent aussi les dix révisions conservées ; les catalogues observés de 454 modèles et une régression de 601 modèles tiennent sans troncature. Un dépassement est un refus visible, jamais une liste silencieusement coupée à 100 ou 500 modèles.

## Ajout guidé

Ollama : `http://127.0.0.1:11434/v1`, pi-ai ; LiteLLM : `http://127.0.0.1:4000/v1`, pi-ai (remplacer par l’endpoint existant vérifié, sans redéploiement) ; OpenRouter : `https://openrouter.ai/api/v1`, pi-ai. Ces valeurs sont des points de départ, pas des connexions ni des générations vérifiées. L’URL peut être renseignée dans les détails avancés **avant** d’ajouter la connexion : son premier enregistrement automatique lie déjà l’UUID à cette destination. Pour un serveur différent, ajouter une nouvelle connexion avec son URL avant validation ; l’édition de l’URL d’un UUID déjà enregistré reste refusée. Nom et transport restent modifiables après ajout. Codex par abonnement ouvre les stratégies natives existantes ; aucun token n’est importé et aucune fausse connexion HTTP n’est créée. Sa disponibilité reste celle du contrôleur natif, notamment Linux x86_64 dans cette base.

## Catalogue client

Les trois profils et les routes directes activées sont servis ensemble par `/v1/models`. L’adaptateur historique garde son comportement par défaut ; le mode Desktop est explicite. Le catalogue expose les protocoles déclarés pour filtrer les routes selon le client, sans inventer de conversion : Chat Completions pour Hermes/OMP, Responses pour Codex, Messages pour Claude. Les profils restent visibles mais refusent sans décideur consenti. Le direct ne sollicite pas le décideur, ne substitue ni fournisseur, ni modèle, ni effort.

Les commandes, formats clients effectivement raccordés, parcours et limites de visibilité native sont consignés dans `../host-adapters/README.md` et les preuves de cette tranche. Un JSON généré ou un CLI factice ne qualifie pas un sélecteur natif ; les essais Mac et le build natif sont la continuation de livraison, pas un résultat Linux.
