**Verdict : NO-GO sur le code de livraison dans le périmètre revu.** Ce verdict ne concerne ni le cœur ni le benchmark déjà déclarés GO, et ne constitue pas un GO/NO-GO AL final. Pas de publication, d'appel fournisseur, de modification source ou de mutation Git du dépôt parent. Les commits Git des tests sont des fixtures dans des répertoires temporaires distincts.

## Bloquant concret d'intégrité : identité non liée à l'archive vérifiée

`build_release.py:76-79` inscrit commit et tree dans `manifest.json`, séparément de l'archive ; `certify` (`:83-113`) vérifie le SHA de l'archive et ses membres, mais ne vérifie ni commit ni tree, ni leur relation aux blobs. `SHA256SUMS` ne couvre que l'archive. Reproduction locale : construction d'un bundle d'un commit temporaire réel, remplacement dans le seul manifeste de `commit` par 40 zéros et `tree` par 40 uns, sans toucher l'archive ni SHA256SUMS ; la certification a réussi. Ainsi même une empreinte d'archive obtenue séparément ne permet pas d'établir le commit prétendu par un manifeste altéré. Les mises en garde d'INSTALL sur l'absence de signature sont exactes, mais ne suffisent pas à établir l'identité demandée. Il faut une liaison vérifiable à une identité de commit de confiance ou une authentification indépendante du manifeste entier, avec vérification explicite de l'identité attendue. Aucun défaut de sûreté d'extraction n'est déduit de ce constat.

## Anomalie de livraison concrète — Python 3.13

`certify` exécute `python -m unittest discover -s tests` avec `check=True` quand `tests` existe (`build_release.py:128-132`). Le fichier réel `tests/test_landing.py` exécute ses assertions à l'import, mais ne définit aucun cas unittest. Avec Python **3.13.5**, cette commande a effectivement imprimé `OK: 8 fragment links, 6 unique IDs, French and prototype disclosures`, puis `Ran 0 tests`, `NO TESTS RAN` et sorti avec statut **5**. La certification d'une archive contenant ce seul module dans `tests` échouerait donc malgré le succès du script, alors qu'INSTALL annonce Python 3.11+. Les fixtures de `test_build_release` utilisent une classe unittest artificielle et ne détectent pas ce cas réel. Ce point est une panne de livraison, distincte du bloquant d'intégrité ; il n'est pas présenté comme une vulnérabilité de sécurité. Aucun build ni certification du commit candidat complet n'a été effectué.
