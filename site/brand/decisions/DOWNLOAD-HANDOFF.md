## Entrée minimale, hors Git

Release prépare un dossier privé contenant `manifest.json` et seulement les installateurs revus à sa racine. Aucun téléchargement réseau dans le build. Depuis `site/` :

```sh
OMR_DOWNLOADS_MANIFEST=/chemin/absolu/manifest.json npm run build
```

Le JSON contient exactement une clé `artifacts` (tableau). Chaque entrée contient exactement ces champs :

- `version` : version SemVer numérique `X.Y.Z`, suffixe prérelease alphanumérique/points/tirets permis ; `os` : `macos`, `windows`, `linux` ; `arch` : `arm64` ou `x64` (Windows/Linux : x64 dans ce raccord).
- `file` : `omr-{version}-{os}-{arch}.{extension}` ; extensions autorisées : macOS `dmg`, Windows `exe`/`msi`, Linux `deb`/`AppImage`. Release renomme les fichiers sans changer leurs octets. Pas de source, ZIP, archive de preuves, chemin, URL privée ou jeton.
- `bytes` : taille exacte positive en octets ; `sha256` : 64 chiffres hexadécimaux minuscules ; `sourceCommit` : SHA Git exact de 40 chiffres hexadécimaux minuscules du produit revu, pas du site.
- `prerelease` : booléen GitHub explicite et identique pour tous les artefacts d’une même version ; il est affiché et contrôlé contre la release distante. Une version avec suffixe SemVer prérelease impose `true` ; une version numérique peut être stable ou prérelease. Pour un build local sans statut GitHub, une version numérique accepte aussi `null`, sans étiquette de statut : la garde de publication existante refuse encore cette valeur. Une prerelease ne peut pas être promue implicitement.
- `releaseApproved` : booléen, explicitement `true` seulement après vérification des preuves par release ; `native` : `verified` ou `unverified` ; `generation` : `verified` ou `synthetic-only`.
- `trust` : `macos-notarized`, `macos-adhoc-blocked`, `windows-signed`, `windows-unsigned`, `linux-unsigned`, ou `unverified`. Ces valeurs décrivent la confiance réelle, jamais une déduction du nom du fichier.

Aucun exemple JSON activable ni paquet fixture n'est livré dans les sources publiables. Les tests fabriquent uniquement des octets synthétiques dans des dossiers temporaires ignorés ; ils ne prouvent ni installation ni génération réelle.

## Admission et sortie

Un paquet devient un lien uniquement si release l'approuve, le parcours natif est vérifié, la confiance est connue et compatible avec l'OS, et ses taille/SHA-256 correspondent aux octets d'un fichier régulier sans symlink. `macos-adhoc-blocked` et `unverified` sont inéligibles : pas de contournement de Gatekeeper. Les états de qualification, dont `generation: synthetic-only`, restent dans les preuves privées et ne sont pas des annotations produit ; une génération synthétique ne prouve pas un parcours fournisseur réel. Les notices utiles à l’utilisateur, comme la prérelease et l’avertissement Windows non signé, restent affichées. Windows non qualifié reste sans lien.

Paquet absent, incomplet, non approuvé, hash/taille incohérents ou confiance bloquante : aucune copie, aucun lien. JSON invalide, champ supplémentaire, doublon, chemin/nom non autorisé ou collision dans le répertoire de sortie : build en erreur plutôt que diffusion implicite. Les versions doivent respecter SemVer sans métadonnées de build : pas de zéro initial dans un nombre ni de composant prérelease vide. Les paquets d’une même version doivent partager le même commit produit et le même statut de prérelease. Un catalogue peut conserver plusieurs versions sans modifier les identités ni les octets des anciens paquets ; version, source et statut suivent chaque paquet, sans identité globale empruntée au premier. La garde de publication contrôle toujours les preuves de la nouvelle release et la conservation exacte des téléchargements historiques. Aucun chemin privé ni champ arbitraire du manifeste n'entre dans le HTML.

Le build nettoie `dist/`, copie uniquement les octets admis sous `/downloads/{version}/{file}`, génère `{file}.sha256` au format `SHA256  filename`, et expose version, OS, architecture, octets, hash, source exacte et confiance dans la section existante. Le checksum est un lien texte natif ; aucune API, dépendance ou JS client ajouté. Plusieurs formats peuvent coexister pour Linux/Windows.

## Contrôle des destinations

Pour un nouveau fichier, une réponse HTTP 404 exacte est nécessaire pour chaque URL de paquet et de checksum ; toute autre réponse, redirection ou erreur réseau refuse la publication. Le mode explicite `--landing-only` ne crée aucun chemin de téléchargement : le manifeste d'artefacts et leurs sidecars doivent couvrir exactement les téléchargements du reçu épinglé, les octets locaux et publics doivent correspondre au reçu (GET 200 sans redirection), et aucun téléchargement supplémentaire n'est accepté. Pour les seuls paquets historiques 0.1.0, `--landing-only --historical-manifest /chemin/manifest-historique.json` vérifie le manifeste d'origine épinglé, ses métadonnées exactes augmentées uniquement de `prerelease: true`, le commit et l'objet tag signé historiques ainsi que la référence distante. Le brouillon historique n'est pas considéré comme immuable ni comme une nouvelle release ; les reçus historiques attestent une distribution passée, pas une reproductibilité des builds. Tout autre cas reste soumis aux contrôles de nouvelle release. Les contrôles de destination, de payload, d'immutabilité du dépôt et d'octets locaux et publics restent obligatoires. Sans ce drapeau, les règles de nouveaux chemins restent inchangées. Les anciennes versions doivent rester présentes à l'identique dans le payload. `python3 site/scripts/check_retained_downloads.py /chemin/payload/site /chemin/payload-final-manifest.json SHA256_DU_MANIFESTE` vérifie les fichiers `downloads/` de l'ancien manifeste de payload contre leurs tailles et empreintes ; le SHA du manifeste doit provenir du reçu accepté. Ce contrôle local ne vérifie pas la destination distante. Ce contrôle seul ne rend pas un déploiement atomique et ne remplace pas la vérification des tags, notes et du payload juste avant publication.
